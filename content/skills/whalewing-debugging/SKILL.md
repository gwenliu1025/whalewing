# 先找根因再修

铁律：没查清根因，不提修复。头痛医头的修补等于失败。越是赶时间、越觉得“改一下试试”就行、越是已经试过几次，越要按这里走。

## 一、查根因

1. **读完错误信息**：完整的报错、堆栈、警告、行号、文件路径和错误码，常常已经写着答案。
2. **稳定复现**：确定确切步骤、是否每次都发生。复现不了就继续收集数据，不猜。
3. **看最近变了什么**：代码差异、最近提交、新依赖、配置和环境差异。
4. **多组件系统先打点再下结论**：请求经过多层（前端、接口、服务、数据库，或流水线、构建、签名）时，在每个边界记录进入和离开的数据、配置和环境是否传到，跑一次看清断在哪一层，再深入那一层。
5. **沿数据流往回追**：坏值在调用栈深处出现时，逐层追问“谁传进来的”，一直追到源头，在源头修，不在出错点打补丁。

线上和共享环境先做有时间范围的只读调查：固定环境、时间段和请求标识，区分日志里看到的、推断的和已经确认的。不凭单个错误码定因。重启、迁移、改配置、回滚等动作需要员工明确授权，并事先说明对象、影响、验证和回退办法。

## 二、找规律

- 在同一工程里找相似且正常工作的实现，逐项列出它和出错处的差异，再小的差异也不要先假定“不可能有关”。
- 照着某个参考实现做的，把参考完整读一遍，不要扫一眼就套用。
- 弄清这处代码依赖的组件、配置、环境和隐含假设。

## 三、假设与验证

- 一次只提一个明确假设：“我认为根因是 X，因为 Y”。
- 用最小的改动验证，一次只改一个变量。
- 不成立就提新假设，不在上面叠加修改。不懂就直说不懂，继续查或请员工提供信息。

## 四、修复

1. 先写能复现问题的失败用例，自动化测试优先，没有测试框架就写一次性脚本；研发任务按 `whalewing-coding` 的测试先行做。
2. 针对根因只做一处修改，不顺手重构、不夹带改进。
3. 复验：原失败输入通过、其他测试没有坏、问题在真实入口确实消失。
4. 修复无效就停下，数一数试了几次：不到三次，带着新信息回到第一步；**三次以上**（每次修复都在别处冒出新问题、需要大规模改动才能修），停止继续修补，和员工讨论架构或做法本身是否有问题。

## 危险信号

出现下面这些念头，就回到第一步：“先临时修一下，回头再查”“改改 X 看行不行”“一次改几处再跑测试”“跳过测试，我手动看过了”“大概是 X”“不太懂但这样也许行”“再试一次”（已经试过两次以上）。员工问“真的这样吗”“能看到证据吗”“别猜了”，说明你在没有证据的情况下下结论了。

## 确实不是代码问题时

查完发现是环境、时序或外部依赖造成的：写下查了什么、排除了什么，加上合适的处理（超时、重试、清楚的报错）和便于下次定位的日志。大多数“查不到根因”其实是没查完。

## 退出

报告根因和证据（复现步骤、关键日志或数据、验证假设的结果）、修改位置、复验结果和没验证的范围；区分本地、测试和线上的结论。根因查清并复验通过，或清楚报告阻断后即退出。
