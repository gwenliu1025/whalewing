# 编码：计划、测试先行与完成前验证

## 先读工程

先读目标工程的规则文件、构建和测试配置、最近的同类实现和直接调用方，再决定改法。保留现有改动，只改本任务需要的地方；工程已有的约定（目录、命名、大文件还是小文件）照旧，不擅自重组。

## 多步任务先写计划

需求已经确认、要改多个文件或分多步完成时，先写计划，读者是没看过这个工程的能干工程师。计划写清他自己猜不到的决定：

- **开头**：目标一句话；做法两三句；技术栈；对应的需求或设计文档位置。
- **全局约束**：版本下限、依赖限制、命名和文案规则、平台要求，每条一行，数值照原文抄。
- **重点检查**：需求没写、但最可能坑到用户的五种输入或失败情况，各写一行期望行为，并把对应测试落到负责的任务里。
- **文件结构**：要新建或修改哪些文件、各管什么；一起变化的文件放一起，按职责拆，不按技术层拆。
- **任务**：每个任务是能单独测试、能被单独驳回的最小单元。写明涉及文件、它依赖和对外提供的接口（准确的名称、参数和返回值）；步骤按“写失败测试、运行看它失败、实现、运行看它通过、提交”排列，测试步骤给出测试名和断言，代码步骤给出签名和需求里定死的数值。

计划放在员工或工程约定的位置，没有约定就问。需求涉及几个独立子系统时，拆成几份计划，每份都能单独交付可用的成果。

## 测试先行

新功能、修缺陷、重构和行为变更都适用。例外（一次性原型、生成代码、纯配置）先问员工。

1. **红**：写一个最小测试，描述一种行为，名字说清楚测什么，尽量测真实代码，不得已才用模拟对象。
2. **确认红**：运行它，确认是失败而不是报错，失败信息符合预期，失败原因是功能缺失而不是拼写错误。测试直接通过，说明测的是已有行为，改测试。
3. **绿**：写刚好让测试通过的最简代码，不加需求之外的选项和功能。
4. **确认绿**：这个测试通过，**工程的完整测试命令**也通过，输出没有新的错误和警告。测试失败就改代码，不改测试。
5. **整理**：只在全绿之后去重、改名、提取函数，并保持全绿。

先写了实现再补测试，测试一上来就是绿的，证明不了它测对了东西。修缺陷时，回归测试要经过“去掉修复会失败、恢复修复会通过”的验证。

## 完成前验证

说“通过、修好了、完成了”之前，必须在这一轮实际运行能证明这句话的命令，读完整输出和退出码，数清失败数，再下结论：

| 说法 | 需要的证据 | 不够的 |
| --- | --- | --- |
| 测试通过 | 本轮测试输出 0 失败 | 上一次的结果、“应该能过” |
| 构建成功 | 构建命令退出码 0 | 代码检查通过 |
| 缺陷已修 | 原失败输入在真实入口复验通过 | 改了代码、推测已修好 |
| 需求已满足 | 逐条对照需求的检查清单 | 测试全绿 |
| 子代理已完成 | 自己看过实际改动和结果 | 子代理报告成功 |

用到“应该”“大概”“看起来”时，说明还没验证。完整测试里出现的失败，哪怕不是你造成的，也要点名写进汇报。

## 退出

交付改动和入口、实际运行的命令与结果、原失败的复验、受影响的调用方、恢复方法和没验证的范围。编译通过、本地自测、隔离运行、线上验收和发布分开表述，没部署就不说上线。完成当前要求即退出，不额外重构。
